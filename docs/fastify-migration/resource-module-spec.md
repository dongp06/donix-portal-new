# Fastify resource module specification

Status: implemented for the Fastify staging, publish, public delivery, owner
preview and storage-reconciliation slice. Multipart staging is bounded and
streamed to a temporary file; resource public download/image delivery verifies
size/hash and streams from disk; maintenance removes abandoned staged files
and claims a database-backed expiring worker lock. Object storage and optional
malware scanning remain deployment decisions.

## Scope

Resources are files attached to an admin-created post with `type=resource`.
The browser may upload a file, but it never chooses a filesystem path or a
storage key. Fastify owns validation, staging, publication state and delivery
authorization.

## Limits

```text
one multipart file per request
50 MiB per resource file
20 files per resource version
2 MiB maximum inline source preview
```

The global Fastify multipart parser accepts 50 MiB and a bounded field/part
count. Files are streamed to a mode-0600 temporary file and are removed after
the mutation completes. Image media still applies its own 10 MiB limit in
`MediaStorageService`.

## Storage contract

```text
RESOURCE_UPLOAD_DIR/<yyyy>/<mm>/<dd>/<random-40-hex>.bin
```

`storageKey` is generated by the server and persisted in `ResourceFile`.
Storage is outside the web public directory. Client filenames are sanitized
before being stored as metadata and used in `Content-Disposition`.

Allowed extensions are code/text (`js`, `ts`, `tsx`, `jsx`, `json`, `py`,
`html`, `css`, `md`, `txt`, `sql`, `yaml`, `yml`, `xml`, `csv`), archives
(`zip`, `rar`, `7z`), PDF and validated image formats (`png`, `jpg`, `jpeg`,
`gif`, `webp`). Every file must pass:

1. extension allowlist;
2. declared MIME allowlist;
3. magic-byte check for binary formats;
4. strict UTF-8 and no NUL bytes for source-previewable text;
5. size limit;
6. generated storage-key/path traversal check.

## State machine

```text
upload
  -> ResourceFile.status=staged, resourceVersionId=NULL

create resource post
  -> Resource + ResourceVersion
  -> staged files atomically become active and attach to version

published post/version
  -> public list/detail and file delivery become eligible

delete staged file
  -> staged -> deleting -> filesystem remove -> metadata delete
```

Only the owner may stage, remove or preview a staged file. A staged file must
belong to the current owner and cannot already be attached to a version.

## Routes

### Public/read

```text
GET /api/resources?q=&limit=
GET /api/resources/post/:slug
GET /api/resources/:id
GET /api/resources/files/:id/preview
GET /api/resources/files/:id/download
GET /api/resources/files/:id/view
```

Public resource metadata requires an active resource, a published post, a
non-deleted post, a published version and active files. Preview/download/view
resolve the optional session cookie server-side; no user id is accepted from
the query or request body.

### Owner/admin

```text
POST /api/m/<permit>
  permit internal path: POST /api/admin/resources/upload

DELETE /api/m/<permit>
  permit internal path: DELETE /api/admin/resources/files/:id

GET /api/admin/resources/files/:id/preview
```

Upload and delete are capability-gateway mutations. Direct admin mutation
paths are not registered as public handlers. The staged preview is a
cookie-authenticated owner read and returns 404 to non-owner/non-staff callers
to preserve the admin surface cloak.

## Visibility policy

```text
requiresLogin=true  -> guest preview/download/view: 401
showSource=false    -> source preview: 403
allowDownload=false -> download: 403
non-image file      -> image view: 404
```

Downloads increment `ResourceFile.downloadCount` only after the file has
passed publication and access checks. Download and image responses set
`nosniff`, private no-store caching and a sanitized content disposition.

## Remaining production work

- checksum audit/repair is implemented in online maintenance with a rotating
  bounded batch (`TB_STORAGE_CHECKSUM_MAX_FILES`, default 256; `0` for a full
  pass); repeated mismatches still need an operator alert/recovery policy;
- add object-storage adapter and malware/content-disarm policy if required;
- extend resource-version lifecycle reconciliation for interrupted or partial
  post/version/storage transitions; scheduled-post promotion is handled by the
  Fastify maintenance pass;
- add range/resumable delivery if large-file traffic requires it;
- run staging browser E2E through transport v4 and the real Next rewrite.
